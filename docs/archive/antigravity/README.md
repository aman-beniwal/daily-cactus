# Running the Daily Cactus on Google Antigravity (Gemini)

A two-day A/B test: run the two editorial routines on Gemini via Antigravity's
scheduled desktop tasks, instead of the Claude Code Routines, and compare the
output. Nothing else in the pipeline changes — `fetch.yml`, `select.yml`,
`publish.yml`, and all the bullet/highlight/emphasis logic are Python in GitHub
Actions and don't care which model wrote the draft.

## Where Antigravity slots in

```
fetch.yml (Actions)            → feeds/digest_lean.json
   ↓
TASK A: SELECT  (Antigravity)  → selections/<date>.json   ← paste TASK_A_SELECT.md
   ↓
select.yml (Actions)           → feeds/selected/<date>.json  (full article text)
   ↓
TASK B: WRITE   (Antigravity)  → drafts/<date>.json       ← paste TASK_B_WRITE.md
   ↓
publish.yml (Actions)          → assembles + deploys the live edition
```

## Setup checklist

1. **Merge the workflow-trigger PR first.** `select.yml`/`publish.yml` used to
   fire only on `claude/**` pushes; the PR adds `gemini/**` (and `main`) so an
   Antigravity agent's push actually triggers the pipeline. Without it the test
   silently produces nothing.

2. **Install Antigravity desktop** and sign in with a Google account that has
   Gemini access. You want the desktop app — it's the one with scheduled
   background tasks.

3. **Give it GitHub push access — a token, not an MCP.** The task only needs
   `git clone/commit/push`, so use Antigravity's GitHub connection, or a
   fine-grained PAT scoped to `AmanBeni/daily-cactus` with **Contents:
   read/write** and **Workflows: read/write**. You configure this in
   Antigravity yourself; it never goes into the pasted prompt. (An MCP server
   wraps GitHub's *API* — the wrong tool for "push one file.")

4. **Create Task A — SELECT.**
   - Prompt: the full contents of [`TASK_A_SELECT.md`](TASK_A_SELECT.md).
   - Model: `gemini-2.5-flash` (cheap, fast, more than enough — upgrade later
     only if the editorial quality needs it).
   - Schedule: ~30 min after `fetch.yml`'s daily run (check its time in the
     repo's **Actions** tab), timezone Asia/Kolkata.

5. **Create Task B — WRITE.**
   - Prompt: the full contents of [`TASK_B_WRITE.md`](TASK_B_WRITE.md).
   - Same model.
   - Schedule: ~45 min after Task A. That gap is where `select.yml` fetches the
     full article text between the two stages.

6. **Pause the Claude Code Routines for the test.** If both produce a draft for
   the same date, `publish.yml` assembles whichever lands first and skips the
   other (editions are immutable) — so leaving Claude running would mean you're
   not actually testing Gemini.

## Day-one sanity check (so you're not debugging blind)

- After Task A runs, open the repo's **Actions** tab and confirm
  **"Select — Full-text fetch"** fired. If Task A committed a
  `selections/<date>.json` but that workflow didn't run, the trigger wiring is
  the problem — merge the PR in step 1.
- After Task B runs, confirm **"Publish Daily Cactus"** fired and the live site
  shows the new date.

## Getting the data back for analysis

Nothing is lost versus the Claude flow. Every run commits
`selections/<date>.json` and `drafts/<date>.json` to the repo, Actions logs the
fetch/publish steps, and Antigravity keeps its own task logs. To compare the two
days against the Claude editions, the drafts and editions are all in git —
diff them exactly as before.

## If the test succeeds

Making it permanent should drop the copy-paste entirely: either the Antigravity
SDK/CLI or a small Gemini-API script in GitHub Actions, reading the prompt
straight from the repo file. At that point `TASK_A/B_*.md` (and this folder) can
be deleted. They exist only so the two-day test needs zero code.

---

`TASK_A_SELECT.md` and `TASK_B_WRITE.md` are generated by
[`build_tasks.py`](build_tasks.py) from the canonical `ROUTINE_PROMPT_A.md` /
`ROUTINE_PROMPT_B.md`. If you change a canonical prompt, re-run
`python antigravity/build_tasks.py` and re-paste.
